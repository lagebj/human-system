# Writing Voice Workflow

**Scope:** This workflow is for ordinary communication that should preserve the author's voice but is not reader-facing Human System public material.

Use this for:

- peer-to-peer work replies
- Teams/Slack status updates
- parent/coaching messages
- meeting agendas
- professional outreach
- strategy notes
- coding-agent prompts
- operational documentation

**Not for:** public Human System papers, essays, notes, or web pages. Those use the `public-writing` skill with `public-language.md`.

## Required reading

1. `resources/source/writing_voice/public-language.md` for general authorship principles (applies broadly, not just to public material)
2. `resources/context/OPERATING_CONTEXT.md` sections 1, 2, 16, and 17 for project memory
3. `resources/source/core_stance/who_am_i.md` when personal/professional voice matters

## Response posture

- Direct, human, practical.
- Reflective without becoming ornate.
- Simple words, complex thought.
- Avoid generic leadership or consultancy language.
- Keep copy-paste outputs usable.
- Use Norwegian only when requested or when the user asks for Norwegian text.

## Important boundaries

Do not apply the manuscript-only Manuscript Voice Guide, Writing Working Agreement, Editing Charter, or Pattern Ledger unless the user explicitly asks for manuscript/book prose.

For normal work messages, emails, Teams updates, parent messages, coding prompts, or strategy notes, clarity and usefulness matter more than manuscript voice constraints.

For reader-facing Human System material (papers, essays, public notes, web pages), use the `public-writing` skill instead. That skill applies the full public-language authorship model including epistemic stance, uncertainty preservation, and scaffolding isolation.

## Common output types

- Peer-to-peer work reply.
- Teams status update.
- Parent/coaching message.
- Meeting agenda.
- Professional outreach.
- Strategy note.
- Coding-agent prompt.

## Quality check

Before returning text, check:

- Would the user actually send this?
- Is it too defensive?
- Is it too formal?
- Did it smuggle in a technical solution the user did not want to force?
- Does it preserve the user's stance without over-explaining it?
